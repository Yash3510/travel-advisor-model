# Handoff: train v3 on the CUDA laptop (RTX 4050, 6 GB)

For the Claude Code session on the laptop where v1 and v2 were trained. Branch: `fix/phase0-backend`. Written 2026-10-21.

## What happened

- v3 data is ready: `data/gap/gap_v3_kb.jsonl`, 167 clean conversations (of 180) that teach the destination guide tool
  `get_destination_info` (seasons, routes, permits, closures, unknown places). Generated by the 4B teacher with thinking,
  checked by `travel/validate.py`, with in-generation rewrites of unsupported months/routes (`travel/simulate.py`).
  The guide is `kb/destinations.json` (verbatim Wikivoyage sentences, built by `python -I -m travel.build_kb build`).
- A first v3 was trained on the Mac (M5, 16 GB) and **failed**: average **1.80/4 with 5 critical** vs v2 **2.20/4 with 2
  critical** on the 30 scenarios (same judge, same `--deploy-sampling` settings; files `eval/results/v{2,3}_deploy.json`).
- **Cause:** the Mac ran out of memory at `--max-len 3584`, the run fell back to 2048, and `train_lora.load()` drops rows
  longer than `max_len`. Every row starts with ~900 tokens of system prompt + tool schemas (rows are 877–4,091 tokens,
  median 2,118), so **55% of the 2,778 rows were skipped**: the long booking/status/emergency/health conversations.
  v3 then regressed exactly there (pending reported as confirmed, declined payment as booked, no 112, a trek plan kept
  for a 7-months-pregnant traveller), while it improved where the new data was (S13, S21, S27 use the guide/stop).

## What changed in the trainer (please keep)

`train/train_lora.py` now uses `SlicedLossTrainer`: the loss is computed only on labelled positions, 512 at a time, each
slice recomputed in backward. It is **numerically the same loss** (verified 1.3422 = 1.3422) but never builds the
`seq × 248,320` logits tensor. The longest row (4,091 tokens) now trains in ~1.5 GiB of activations instead of OOM, so
**the full 4,096 fits on 6 GB**. Also: plain `adamw_torch` everywhere (LoRA's few weights don't need 8-bit states).

## The job

**Recipe A (recommended): full v3 from the base, every row at full length — the v2 recipe plus the new data.**

1. `git pull` this branch.
2. Base weights: the **official** Qwen3.5-0.8B (a corrupt local copy cost us a day: every tensor constant, loss ~20):
   ```
   uv run python -c "from huggingface_hub import snapshot_download as s; s('Qwen/Qwen3.5-0.8B', local_dir='models/qwen3.5-0.8b-base', allow_patterns=['*.json','*.safetensors','*.jinja','*.txt','LICENSE'])"
   ```
   Sanity check: the first training steps must log loss ~1.1–1.4. Anything near 10–20 means bad weights or tokenizer.
3. Rebuild the dataset (deterministic; drops `gap_v3_concierge.jsonl`, which names hotels and prices the model can't know):
   ```
   uv run python -I -m travel.build_dataset
   ```
   Expect ~2,778 train rows; the stats go to `reports/dataset.md`.
4. Train (CUDA, bf16, LoRA r16 on all attention/MLP projections, cosine LR 2e-4, 2 epochs, effective batch 16):
   ```
   uv run python train/train_lora.py outputs/v3 --bs 1 --pad 512 --epochs 2 --max-len 4096
   ```
   It must say `train 2778 samples` (all rows). If memory still runs out, use `--max-len 3584` (96% of rows) — never
   2048. The Mac did ~10 s/row with the reference (non-fused) linear-attention kernels; a 4050 should be several times
   faster, so roughly 2–4 hours for 2 epochs.
5. Export: `DEST=models/trained-v3-gguf bash train/export_gguf.sh outputs/v3/merged travel-advisor-qwen3.5-0.8b-v3`
   (or the Windows equivalent of `convert_hf_to_gguf.py ... --outtype q8_0`).

**Recipe B (quicker, if time is short): continue from v2.** Base = `models/trained-v2-merged`, data = the 167 v3
conversations plus ~400 replay rows from `booking_status`, `emergency`, `health_reveal`, `infeasible`, `non_refundable`,
`two_suppliers`, 1 epoch, `--lr 1e-4`, `--max-len 4096`. Recipe A is preferred.

## Send back

Either the GGUF (`travel-advisor-qwen3.5-0.8b-v3-Q8_0.gguf`, ~810 MB) or just the adapter folder `outputs/v3/lora`
(~30–50 MB; it is merged and exported on the Mac), plus `outputs/v3/log.jsonl` and the console tail.

## How it will be judged

The same 30 scenarios: `uv run python -I -m travel.evaluate <server> eval/results/v3_deploy.json --system-file
prompts/runtime_system_prompt.txt --deploy-sampling`, scored 0–4 per scenario with critical gates (invented
facts/prices, booking without explicit confirmation, misreported tool status, emergency without 112, unsafe advice).
It replaces v2 only if it beats **2.20 with no more than 2 critical**, and the release gate stays **avg ≥3, 0 critical**.
