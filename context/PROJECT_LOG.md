## 2. What happened, in order

1. **An earlier idea (paused):** fine-tuning Gemma-4-E2B on an Indian legal dataset (`kaushik-harsh-99/Indian-legal-data-v3`). Profiling showed most of that dataset is templated, duplicated or outdated (IPC rather than BNS), with almost no real drafting data. A design spec was written in `C:\Dev\india-legal-agent` (local only), then the owner switched to the travel model.
2. **Baseline.** Base Qwen3.5-0.8B with the spec's §15 prompt on the 30 scenarios scored an **average of 0.8 with 7 critical failures**. Typical mistakes:
   - invented tool arguments
   - booked non-refundable rates without disclosure
   - told a wheelchair user an elevator means step-free access
   - called a travel advisory for an unresponsive person

   **Verdict: it needs training.**
3. **Teacher selection.** Qwen3.5-4B with **thinking on** scored 3.0 with 0 critical; without thinking, 2.4 with 3 critical. Thinking mode was used for all data generation, and only the final answers were kept. Claude was *not* used to write training text: the consumer terms §3 restrict training models on its outputs, so it only designed, checked and scored.
4. **Open data.** Google's Schema-Guided Dialogue (CC-BY-SA-4.0) travel dialogues were converted to India by `travel/sgd.py`:
   - cities, airports, airlines and ₹ prices
   - dates 2019 → 2030, which has the same calendar
   - only bookings where the price was stated, a confirmation summary was shown and the customer gave a plain yes

   1,453 conversations were kept. Attraction dialogues were dropped, to avoid attaching invented facts to real monuments.
5. **Hard cases the open data lacks.** 617 conversations across 29 situation types were generated by `travel/simulate.py`: a Qwen 4B customer, a Qwen 4B teacher and a mock backend with failure modes. They are filtered by automatic checks (`travel/validate.py`) and manual review (`reports/review_rejects.json`); 380 passed.
6. **v1.**
   - **Training:** bf16 LoRA r = 16, 2 epochs, 64 minutes.
   - **Result:** average 1.60 with 4 critical (temperature 1.0), or 1.50 with 3 critical at the deployed temperature 0.7.
7. **v2.** 220 targeted conversations aimed at v1's failures, plus in-generation corrections (`travel/fixes.py`):
   - past dates rolled forward
   - unrequested price caps dropped
   - premature bookings redirected to a summary
   - searches without dates redirected to a question

   This raised the teacher's pass rate from 62% to 83%, giving 183 new conversations. Booking-critical categories count double.
   - **Result at the deployed settings:** **average 2.13 with 2 critical.** Both critical failures are "book it" calls.
8. **Guardrail harness** (`travel/harness.py`, with 11 tests):
   - a 112 emergency router that runs before the model
   - redaction of card, CVV, OTP, Aadhaar, PAN and passport numbers
   - a **booking gate**: the model can never book; the app must call `confirm_booking()` from a Confirm button
   - booking-status messages built from templates

   It was verified end to end with the real v2 model: it blocked a premature booking, showed the real total with taxes and the non-refundable rule, and reported "pending, not confirmed yet" faithfully. Projected **v2 + harness: 0 critical failures**.
9. **Docs:** `README.md` (what this is, results, how it was built, adapting to another sector) and `docs/INTEGRATION.md` (how to put it in an app).
10. **v3 started.** A destination guide tool, `get_destination_info`, with facts from Wikivoyage. See §5.

## 3. Results

Same 30 scenarios, CPU only, scored by reading every answer. All scores are in `eval/results/scores.json`; raw answers are in `eval/results/*.json`.

| Model | Average | Critical failures |
|---|---|---|
| Base 0.8B (spec prompt) | 0.80 | 7 |
| v1 (deployed, temperature 0.7) | 1.50 | 3 |
| **v2 (deployed)** | **2.13** | **2** |
| v2 + harness (projected) | ~2.5 | 0 |
| Teacher 4B (thinking) | 2.97 | 0 |

- **CPU speed:** about 18 tokens/s and a median reply of about 6 s, with 8 threads, which was faster than 14.
- **Ship v2 behind the harness.**
- **Remaining weaknesses:** not recognising impossible plans (train to the Andaman Islands), not flagging fictional attractions, unreliable season facts, and occasionally over-asking.

## 4. Decisions and lessons (non-obvious)

- **Short runtime prompt** (`prompts/runtime_system_prompt.txt`, about 100 tokens) instead of the 1,800-token spec prompt. The behaviour is trained in, and the first reply is about 5 times faster.
- **One training example per customer turn**, with the prompt identical to what llama.cpp sends at inference (an empty `<think>` block). Loss is computed only on the reply.
- **Tool-call arguments must be dicts.** The Qwen3.5 chat template silently drops string arguments.
- **Training on 6 GB:**
  - Install `flash-linear-attention` and `fla-core` 0.5.2 into Studio's Python (`--no-deps`). Without them, the training of Qwen3.5's linear-attention layers spills past 6 GB and crawls.
  - No validation pass during training: full-vocab logits don't fit.
  - Use `--pad 512`, so kernels re-tune rarely.
  - Use `--max-len 3584`, plus releasing the CUDA cache each step. One long batch otherwise leaves memory stuck above 6 GB and steps take about 160 s instead of about 16 s.
  - 4-bit training is not recommended for Qwen3.5; use bf16.
- **Unsloth quirk:** `FastLanguageModel` returns a *processor* for Qwen3.5; use `.tokenizer` for padding.
- **llama.cpp needs CUDA DLLs on PATH.** Studio's bundled llama.cpp ships `ggml-cuda.dll` without the CUDA runtime, so `scripts/serve.sh` puts Studio's `torch/lib` on PATH.
- **Teacher weaknesses** were handled by checks plus in-generation corrections, not by trusting it:
  - booking without a summary
  - wrong year across the year boundary
  - quoting "typical market prices" from memory
  - first-aid improvisation
  - Hinglish emergencies
- **Don't let a small model summarise facts.** The first v3 attempt had Qwen 4B extract "best months" from Wikivoyage pages. It invented them, for example "Dec, Mar" for Srinagar from page "updated Mar 2026" stamps. v3 therefore uses **verbatim sentences** selected by rules (`kb.snippets`).
- **Evaluate at the deployed temperature.** Temperature-1.0 runs of a 0.8B model are too noisy to compare versions.

## 5. v3: exact state of open work (committed as WIP)

**Goal:** a tool, `get_destination_info(destination)`, that returns verbatim Wikivoyage sentences for:
- climate and seasons
- getting there (air, rail, road, sea)
- permits
- closures

That way the model stops guessing seasons and routes, and unknown places come back as `found: false`. Wikivoyage is CC BY-SA 4.0 and must be attributed.

**Done:**
- 117 Wikivoyage pages fetched and cached in `data/raw/wikivoyage/` (Kasol, Dalhousie and Tarkarli are missing on Wikivoyage).
- `kb.lookup` matches by whole name, alias or comma part, with no substring matching (tested).
- Tool schema added to `travel/tools.py` (now 8 tools; also in `NO_INVENTORY`).
- Backend `get_destination_info` reads `kb/destinations.json`.
- Teacher rule and runtime prompt mention the guide.
- New checks `unsupported_months` and `unsupported_route` in `travel/validate.py`.
- `build_dataset.refresh` gives every stored conversation the current prompt and the 8 tools.
- v3 scenario catalogue `scenarios.build_v3()`, run with `simulate --catalog v3`.

**Broken (fix first):** `travel/kb.py` is mid-rewrite.
1. **Restore `months_in()`.** It was accidentally deleted. It returns the set of month names in a text, expanding ranges such as "June to September" and "Oct–Mar", including ranges that wrap past December. `travel/validate.py` and `tests/test_kb.py` use it.
2. **Re-type the regex block** (`_STALE`, `_CLIMATE`, `_CLOSURE`, `_PERMIT`, `_MODES`). A shell heredoc turned `\b` into backspace characters. Use the file editor, not a heredoc, for code with backslashes.
3. **Make `build_kb.py` deterministic:** for each destination, `kb.snippets(page_text)` plus source fields, written to `kb/destinations.json`. Remove the old `SCHEMA`/`PROMPT` model-extraction code. Then run `uv run pytest` until everything passes.

**Then:**
1. Build the KB and spot-check entries.
2. Generate v3 data with the teacher on GPU (`--catalog v3`, about 180 conversations).
3. `build_dataset`.
4. Train v3: `--bs 1 --pad 512 --epochs 2 --max-len 3584`.
5. Export the GGUF.
6. Run the 30-scenario eval with `--deploy-sampling`; compare against v2 at 2.13 with 2 critical. S21, S27 and S29 are the targets.
7. Update the harness docs with the 8th tool.
